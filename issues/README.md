# Issue 管理

治理版本：g1.0。更新日期：2026-10-09。关联： [ISSUE-003](ISSUE-003.md) / FE-M0-T02。

本目录记录问题事实、变更范围、实施任务和验收结论。阅读入口是 [看板](index.md)，详情从 [模板](template.md) 创建。整体规则见 [协作工作流](../docs/governance/WORKFLOW.md)，执行进度见 [任务看板](../docs/TASK_BOARD.md)。

## 必须先登记的工作

每次需求变更、产品或工程版本更新、Bug 修复都必须先登记或关联一个已有 Issue，再修改实现与基线。流程、模块边界、技术冻结或部署选型变更也必须登记。不能用“改动小”“马上可修完”或“仅改文档”绕过这些事项的 Issue 前置要求。

1. 先读看板与相关历史 Issue，避免重复和漏掉协作分支记录。
2. 取下一个编号，复制模板为 `ISSUE-XXX.md`；填写类型、现象、证据、影响、验收和六份基线评估，在看板登记。
3. 关联实际 Task ID 与 [TASK_BOARD](../docs/TASK_BOARD.md)，明确输入、涉及路径、验收与负责人。
4. 完成修改后登记实际验证、代码或流程解释、交付说明和基线同步结果。
5. 进入 in-review；复核通过后才能 closed。合入与发布使用独立字段，后续发生时再更新。

同一 Issue 可以跟踪同一变更的多个任务；不同范围的新需求应新建 Issue 并互链。外部分支已关闭的 Issue 保留其原状态与来源，本地整合状态单独记录。

## 类型与状态

| 类型 | 使用场景 |
|---|---|
| change | 需求、业务范围、功能或验收口径变化 |
| version | 产品、文档或工程版本升级及兼容变化 |
| bug | 已有行为偏离需求、缺陷与回归 |
| workflow | 协作、治理、任务、验证或交付流程变化 |
| decision | 技术选型、架构边界、部署与其他待定决策 |

状态只使用下列七个值。类型、状态和本地验收结论分别填写。

| 状态 | 含义与转换条件 |
|---|---|
| new | 已登记，尚待分析 |
| triaged | 现象、影响、分流和所需输入已分析 |
| ready | 范围、任务及验收条件明确，可以实施 |
| in-progress | 正在实施，仍有未完成项 |
| in-review | 实施、验证和文档已提交复核，等待验收 |
| closed | 本地验收通过、基线同步完成且证据已记录 |
| blocked | 被具体依赖阻塞，记录原因、解除条件和下一步 |

复核未通过回到 in-progress 并登记失败项；需求或输入不足回到 triaged。解除阻塞后回到实际对应的状态。历史已验收事项发现新回归时新建 bug Issue，保留旧验收事实并互链。

## 每次变更的六份基线评估

每个 Issue 都要逐行填写“有影响 / 无影响 / 待评估”、具体理由、实际更新路径、修订标识和完成状态。未涉及的文档必须写“无影响”及原因，不能留空、默默跳过或为了凑表新建无依据文件。

| 基线 | 评估内容与更新路径 |
|---|---|
| [PRD](../docs/PRD.md) | 需求、页面、范围和验收；更新实际受影响章节或治理说明。供评审参考文档仍保留原文状态 |
| [ROADMAP](../docs/ROADMAP.md) | 阶段、依赖、优先级、里程碑及验收；治理变更只更新相关治理标识，不伪改产品排期 |
| [ARCHITECTURE](../docs/ARCHITECTURE.md) | 模块边界、数据流、接口、状态、部署与技术决策 |
| [TASK_BOARD](../docs/TASK_BOARD.md) | Task ID、Issue、任务输入输出、状态、涉及文件和验证证据 |
| [PROJECT_STATUS](../docs/PROJECT_STATUS.md) | 已有实现、当前阶段、限制、下一步及合入状态 |
| [DOCUMENT_INDEX](../docs/DOCUMENT_INDEX.md) | 新增或更新文档、路径、用途、状态及版本 |

修订记录使用实际 `revision`、`Issue ID` 和日期。一次变更的相关基线同日记录同一 Issue；版本号按各自职责维护，不要求产品、架构、治理版本相等。治理版 g1.0 不替换原产品 PRD 版本。若跨日完成，记录各步实际日期，再登记最终对齐日期，不能倒填未发生的验收。

## 任务、PR、交付与解释的互链

- Issue 详情与任务看板互链：使用稳定 Task ID，任务写出关联 Issue，不能只在评论里描述。
- Issue、PR 与交付说明互链：PR 创建后填写实际 URL；PR 正文包含 Issue/Task 和交付记录。未创建 PR 明确写“未创建”，不能用占位地址。
- 涉及代码时，登记实际代码路径、改变的行为及 `docs/code/<Task ID>.md` 解释路径；代码解释回链 Issue、Task 和交付记录。工程检查脚本与测试同样属于代码改动。
- 仅涉及文档或流程时，写明“无代码影响”和原因，关联流程解释与交付说明；不声称已经实现应用、服务或验证真实接口。
- 验证记录包含执行方式、结果、边界和日期；交付说明含解释摘要，并回链 Issue、Task、验证及独立代码解释文件。

当前治理交付使用 [FE-M0-T02](../docs/delivery/FE-M0-T02.md)，工程检查解释使用 [FE-M0-T02 代码说明](../docs/code/FE-M0-T02.md)，流程解释使用 [WORKFLOW](../docs/governance/WORKFLOW.md)。后续任务应填写自己的实际路径。

## 验收、合入与发布分别记录

Issue closed 和任务 done 都表示本地验收已完成，不能据此宣称 PR 已合入或系统已发布。每个 Issue 单独记录：本地验收、PR 状态、合入提交及日期、发布版本及日期。尚未发生的步骤写“未合入 / 未发布 / 待记录”，不得补成通过。

关闭前必须有完整验收结果、实际验证与局限、六份基线同步结论、交付与解释互链，并由复核记录支持。阻塞、未执行或失败项不得写为 passed；存在这些未完成验收项时保持实际状态。
