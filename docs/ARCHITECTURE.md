               │               │               │

     │  向量数据库   │  │  文档存储     │  │  模型服务(本机) │

## 2. 技术栈选型

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Python | 生态成熟，RAG/LLM 工具链丰富 |

| 关系库 | PostgreSQL | 存需求清单、项目、元数据、版本 |
| Agent 编排 | LangGraph 或 Dify | 需求提取→检索→生成→组装 的工作流编排 |
| 后端 | FastAPI | 提供 API + 静态资源 |
| 前端 | Vue/React（简单工作台） | 审核交互界面 |
| 部署 | Docker + Docker Compose | 打包后一键部署到机房 |

## 3. RAG 管线（核心）

### 3.1 文档解析（知识库入库 & 招标文件）
- 支持 **docx / pdf**。
- 解析**标题层级**（章节/条款/子项）与**表格**。
- 招标文件解析后产出**需求条目清单**；知识库文档解析后产出**结构化块**。

### 3.2 结构化切块（痛点①）
- **按标题层级/条款/表格切分**，而非固定字数。
- 每块保留**父级上下文**（章节路径前缀，如"第3章/3.2/3.2.1"）。
- **表格单独成块**，不拆散。
- 叙述性长文相邻块**重叠 10~20%** 保边界。
- 每块附加**元数据**：来源文档、章节路径、内容类型、适用范围、版本/状态。

```
元数据模型（块 "身份证"）：
  source_doc   : 技术规范书_V2.3.pdf
  section_path : 第3章/3.2/3.2.1
  content_type : 条款 | 表格 | 通用要求
  scope        : IT 系统集成 | 软硬件 | ...
  version      : V2.3
  status       : 有效 | 失效
```

### 3.3 向量化与索引
- 用 **bge-m3** 将块编码为向量，与元数据一并入库。
- 采用**增量索引**：新文档只索引自身，不重建全库。

### 3.4 检索与重排
- **混合检索**：稠密向量检索（语义）+ 稀疏/BM25（专业术语关键词）双路召回。
- **元数据过滤**：检索时限定适用范围、版本状态（杜绝旧版/不相关内容）。
- **重排**：召回 Top50 后由 bge-reranker 精排，取 Top5~8 拼上下文。

### 3.5 生成（多候选）
- 对**每条需求**，用 Qwen3-30B 基于检索上下文生成 **N=3 个候选响应**。
- 候选差异化（详略/表述/角度）。
- 每个候选**强制标注来源引用**（引用哪份文档/章节）。

## 4. Agent 工作流（需求提取 → 生成 → 组装）

用 LangGraph（或 Dify）编排有状态工作流：

```
[上传招标包]
   → parse_docs(解析) 
   → extract_requirements(提取需求条目清单, LLM)
   → [人工确认需求清单]  ← 状态节点，暂停等人工
   → 对每条需求:
        retrieve(混合检索+过滤+重排)
        generate_candidates(生成3个候选, 带引用)
        → [人工逐条挑选/修改]  ← 状态节点，暂停等人工
   → assemble(按章节组装)
   → export_docx(导出)
   → feedback_to_kb(定稿回流知识库)
```

**人在回路**：工作流在"需求确认"和"逐条挑选"两处暂停，等待人工，保证质量与合规。

---

## 5. 知识库管理（痛点②）

- **元数据驱动**：每个条目带来源/版本/适用范围/状态。
- **版本管理**：新版本入库时旧版标"失效"，不再被默认检索命中。
- **去重**：入库时检测重复内容。
- **增量更新**：新增文档只处理自身。
- **合规标注**：区分"企业自有/已授权"来源，禁止未授权内容入库。
- **内容回流**：人工定稿响应可一键入库（带来源项目、适用类型、版本）。

## 6. 合规保障机制（严禁超范围、来源合规）

| 机制 | 实现 |
|---|---|
| 元数据过滤 | 检索限定适用范围与版本，杜绝越界内容 |
| 提示词强约束 | 生成时明确"只响应招标要求，不额外发挥" |
| 超范围校验 | 生成后检查是否含招标未要求内容，超范围则标记/拦截 |
| 来源引用 | 每个候选强制附引用，无来源内容标记"待人工补充" |
| 审计日志 | 记录每条需求的生成、选择、修改痕迹，可追溯 |

## 7. 部署架构（需求5）

```
公司机房服务器 / VM
├── Docker 容器
│   ├── app           # FastAPI 后端 + 前端静态资源
│   ├── vector-db     # 向量库（Milvus/Qdrant/pgvector）
│   ├── postgres      # 关系库（元数据/项目/需求）
│   └── model-api     # 模型服务（Qwen3-30B, bge-m3, reranker）
└── 磁盘存储          # 原始文档 + 索引
```

- 用 **Docker Compose** 一键编排，便于复制到不同 VM。
- 模型服务独立容器，可单独扩容（GPU 节点）。

---

## 8. 数据流概览

1. 招标文件 → 解析 → 需求清单（存 PostgreSQL）。
2. 需求 → RAG 检索（向量库）→ 候选响应（附引用）→ 存需求/响应表。
3. 人工挑选 → 更新响应状态 → 组装 → 导出 docx。
4. 定稿 → 回流知识库（解析+切块+索引）。
