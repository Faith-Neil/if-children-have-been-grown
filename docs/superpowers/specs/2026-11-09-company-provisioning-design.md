# 公司开通与账号归属设计

状态：用户已确认设计，尚未改业务代码，尚未合入。确认日期：2026-11-09。关联 [ISSUE-052](../../../issues/ISSUE-052.md)。

主规格是用户确认的方案 1（公司页扩成「公司 → 用户」工作台）。文末「对话决定」只记录问答里定死的选项。两边冲突时，对话决定覆盖正文表述。

## 1. 要做成什么

平台管理员不属于任何业务公司，顶栏不展示公司名称。平台管理员在公司管理里一次开通公司并创建该公司第一个公司管理员；点进某公司后查看并管理该公司全部公司管理员与普通成员。公司管理员只能看见本公司，并在本公司下创建普通成员。一家公司允许有多个公司管理员。

不做：全局「用户总览」独立导航页；空公司无管理员的开通路径；平台账号出现在公司列表里。

## 2. 角色与权限

| 角色 | 公司列表 | 新建公司 | 公司详情用户列表 | 在公司详情加人 |
|------|----------|----------|------------------|----------------|
| `platform_admin` | 全部业务公司 | 是：同一弹窗建首个 `company_admin` | 该公司全部账号 | 可加 `company_admin` 与 `member` |
| `company_admin` | 仅本公司 | 否 | 本公司全部账号 | 仅可加 `member` |
| `member` | 无入口 | 无 | 无 | 无 |

平台账号：`company_id = system`，不进入 `known_company_ids`，不能作为开通目标，也不能被公司详情列出。

既有 `/admin/users`（UsersPage）若仍对 `company_admin` 可达，可继续用于本公司加人；**本设计主路径是公司管理 → 公司详情**。平台管理员跨公司看人、加人，以公司详情为准，不新增全局用户总览。

## 3. 界面

### 3.1 顶栏

`AppHeaderActions`（或等价壳层）：当会话角色为 `platform_admin` 时，不渲染公司名标签（当前 `companyName(user.company_id)` 会把非 `alpha` 映射成「远山…」）。其他角色行为不变。

### 3.2 公司管理列表

页面：`frontend/web/src/admin/CompanyManagePage.tsx`。

- 平台管理员可见「新建公司」按钮。
- 公司名称可点击进入该公司详情（路由见 §3.4）。
- 停用 / 启用公司、停用确认输入完整公司名、模型与知识库服务配置入口保持现状语义。

### 3.3 新建公司弹窗（同一对话框）

字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| 公司显示名 | 是 | 去首尾空白后非空；不得与已有业务公司显示名重复（按去空白后全文比较） |
| 首个管理员用户名 | 是 | 全局唯一，作为账号 `id` |
| 首个管理员姓名 | 是 | 写入账号 `name`；未另填显示名时同时作为 `display_name` |
| 首个管理员显示名 | 否 | 有则写入 `display_name`，否则用姓名 |
| 初始密码 | 是 | 按平台默认策略走现有 `require_strong_password` |
| 首次登录强制改密 | 否 | 勾选框，**默认勾选**；写入首个管理员的 `must_change_password` |

提交成功后：用简短成功提示展示自动生成的 `company_id` 与管理员用户名，关闭弹窗，并刷新列表。

不提供手工填写 `company_id` 的输入框。

### 3.4 公司详情

路由：`/admin/companies/:companyId`（与壳层现有 `/admin/...` 风格一致；前端路由表按此 path 注册）。

内容：

- 页头：公司显示名、`company_id`、状态（启用/停用）。
- 用户表：用户名、显示名、角色（`company_admin` / `member`）、状态、是否待改密（可选列）。
- 「添加账号」弹窗：用户名、显示名、初始密码、角色（平台管理员：`company_admin` | `member`；公司管理员：固定 `member`）、「首次登录强制改密」勾选（默认勾选）。
- 非本公司的 `company_admin` 访问他人公司详情 → 404 或等价「未找到」（与现有跨租户 404 口径一致）。
- `member` 不可进入。

## 4. 后端

### 4.1 `POST /api/v1/companies`

仅 `platform_admin`（含超级管理员判定与现网一致）。

请求体（示意）：

```json
{
  "name": "示例科技有限公司",
  "admin_username": "acme_admin",
  "admin_name": "张三",
  "admin_password": "……",
  "admin_display_name": "张三",
  "must_change_password": true
}
```

`must_change_password` 缺省为 `true`。

行为（同一持久化事务）：

1. 校验显示名、管理员字段与密码强度。
2. 生成 `company_id`：`co-` + 8 位小写十六进制（或等价短码）；若与已有 `company_id` 冲突则重试，上限有限次，用尽则 500 内部错误。
3. 写入 `service_stores["companies"]`：`status=active`，记录创建人与时间（字段名与现有 company record 对齐；没有的键可新增 `created_at` / `created_by`，不删现有键）。
4. 写入公司显示名：与现有 `company_settings` / `company_display_name` 路径一致，保证列表立刻显示正确名称。
5. 创建首个 `Account`：`role=company_admin`，`company_id` 为新 id，`must_change_password` 取请求值，密码加盐哈希与现有 `hash_password` 一致。
6. 审计：`company.create`（含 `company_id`、操作者、首个管理员 id，不含明文密码）。

响应：公司摘要（同列表项字段）+ 首个管理员的脱敏用户视图（同 `UserModel`）。

错误：

| 条件 | 码 |
|------|-----|
| 非平台管理员 | 403 `FORBIDDEN` |
| 显示名为空 | 422 `VALIDATION_ERROR`（`details.field=name`） |
| 显示名与已有业务公司冲突 | 409 `COMPANY_NAME_DUPLICATED` |
| 用户名已存在 | 409 `DICT_CODE_DUPLICATED`（与现有建用户一致） |
| 密码过弱 | 422 `PASSWORD_WEAK` |

### 4.2 用户列表过滤

`GET /api/v1/users?company_id=`：

- `platform_admin`：可传 `company_id` 只看该公司；不传则保持现有全量（或现网等价）列表行为。公司详情页请求必须带 `company_id`。
- `company_admin`：无论是否传参，只能看本公司；传其他公司 id → 404 `NOT_FOUND`。
- 公司详情列表不得包含 `company_id=system` 的平台账号，也不得混入他司账号。

### 4.3 `POST /api/v1/users`

既有门禁已支持：平台管理员可建 `company_admin` / `member`；公司管理员仅可建本公司 `member`。本设计增量：

- `CreateUserRequest` 增加可选 `must_change_password: bool = true`。
- 创建时写入该字段，不再写死为 `True` 而忽略调用方。
- 公司详情「添加账号」走此接口，`company_id` 为详情公司。

### 4.4 公司停用

语义不变：停用后该公司账号立即退出且不能登录；资料与项目保留；可再启用。开通流不改变停用逻辑。

## 5. 数据与隔离（硬约束）

各公司之间**项目与知识库均强隔离**，开通新公司不得复用他司项目或他司数据集。

### 5.1 项目隔离

- 每个投标项目带且只带一个业务 `company_id`。
- 列表、打开、编辑、导出、成员与检查等读写，只能看见本公司项目；跨公司按现有口径返回 404 `NOT_FOUND`（或等价「未找到」），不得泄漏他司项目名或 id。
- 平台管理员若具备跨公司只读/运维入口，仍须按目标公司过滤，禁止把 A 公司项目挂到 B 公司会话或写入 B 公司命名空间。本设计不新开「跨公司合并项目」能力。

### 5.2 双库数据集隔离

现网两类公司知识库数据集（历史标书 / 资料库）按公司各自创建、各自绑定，**禁止混用**：

| 种类 | 数据集全名约定（现网） |
|------|------------------------|
| 历史标书 `history` | `${company_id}::icg-history` |
| 资料库 `materials` | `${company_id}::icg-material` |

- 「建立 / 确保数据集」必须落在**当前操作所属公司**的 `company_id` 上（调用既有 `dataset_full_name(company_id, kind)` / `ensure_dataset`），为该公司各建一套；不得把已有他司的 dataset id 写入本公司索引，不得检索或上传到他司数据集。
- 新开通公司默认尚无远端数据集；该公司管理员（或具备知识库配置权限的角色）在本公司上下文首次「建立」时创建**本公司**的两套数据集。开通公司 API **不**把任何公司指到共享/全局数据集。
- RAG 检索、上传、同步与审计记录中的数据集绑定必须可追溯到同一 `company_id`；校验失败则拒绝，不得静默回落到他司或无租户数据集。
- 本设计不改 RAG 管道节点本身；只强制租户边界与命名空间在开通与建库路径上不可绕过。

### 5.3 其他

- 不把真实客户凭据写入仓库；测试用合成公司名与账号。
- 关演示（`VITE_DEMO=0`）与生产持久化门禁下，开通与登录须走真实账号链路，不得依赖 demo 快捷登录冒充验收。

## 6. 测试与验收

至少覆盖：

1. 平台管理员顶栏不出现公司名。
2. `POST /companies` 一次成功后列表有公司、可用首个管理员登录；勾选强制改密时登录后须改密；取消勾选时可直接工作（仍受密码强度约束）。
3. 公司详情列出该公司管理员与成员；平台管理员可再加两种角色；公司管理员只能加成员，跨公司 404。
4. 多家公司并存时，A 公司管理员看不到 B 公司用户，也看不到 B 公司项目。
5. A、B 两公司各自 `ensure` 双库后，数据集全名分别为 `A::icg-history` / `A::icg-material` 与 `B::icg-history` / `B::icg-material`，索引中的 dataset id 互不引用；A 的检索/上传不得命中 B 的数据集。
6. 非平台管理员调用 `POST /companies` → 403。
7. 前端单测 / 后端领域单测覆盖新建冲突与 `must_change_password` 传递；有条件时补一条浏览器冒烟（不把内存模式写成生产已通）。

不在本设计声称：已合入 main、已发布、已标任务 done。
