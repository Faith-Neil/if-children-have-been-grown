## 2. 分期计划（8 周 MVP 路径）

### M1 · RAG 最小闭环（第 1–2 周）
**目标**：先把"知识库 → 检索 → 生成"这条最核心的链路跑通，验证 RAG 可行性。

- [ ] 环境搭建：机房部署 Qwen3-30B、bge-m3、bge-reranker（Ollama 或 vLLM）
- [ ] 向量库选型并部署（Milvus / Qdrant / pgvector 三选一）
- [ ] 用少量历史标书做**结构化切块**（按章节/条款/表格）
- [ ] 实现"提问 → 混合检索 → 重排 → 生成回答（带引用）"的最小脚本
- **验收**：对几个典型需求能检索出相关内容并生成带引用的回答

### M2 · Agent 工作流 + 需求提取（第 3–4 周）
**目标**：把单点能力串成"招标文件→需求清单→逐条生成"的工作流。

- [ ] 招标文件解析（docx/pdf，标题层级 + 表格）
- [ ] 需求提取模块（LLM 从招标文件提取需求条目清单）
- [ ] 用 LangGraph（或 Dify）编排工作流，含"需求确认"人工暂停点
- **验收**：上传一份真实招标包，能产出可用的需求清单并逐条生成候选

### M3 · 人工审核工作台（第 5 周）
**目标**：实现"逐条多候选，人工逐条挑"的交互（核心交付形态）。

- [ ] FastAPI 后端 API
- [ ] Web 工作台：需求列表、候选展示（带引用）、选择/修改/重新生成
- [ ] 逐条完成后组装成文档
- **验收**：一个需求能生成 3 个候选，人工可逐条挑选并导出

### M4 · 检索质量优化（第 6 周）
**目标**：针对痛点①，把检索质量做扎实。

- [ ] 切块策略调优（针对真实招标/标书，验证结构切块效果）
- [ ] 混合检索（稠密+稀疏）+ 重排联调
- [ ] 检索质量评测（召回率/命中率），迭代优化
- **验收**：典型需求检索命中率达标

### M5 · 知识库管理（第 7 周）
**目标**：解决痛点②③，知识库可维护、可持续。

- [ ] 元数据模型落地（来源/版本/适用范围/状态）
- [ ] 版本管理与失效内容处理
- [ ] 增量索引 + 内容回流（定稿入知识库）
- **验收**：新增文档可增量入库；旧版本不干扰检索

### M6 · 生产化部署（第 8 周）
**目标**：满足需求 5，交付可上线系统。

- [ ] Docker Compose 打包（后端/向量库/关系库/模型服务）
- [ ] 部署到公司服务器 / VM 并验证
- [ ] 合规保障功能核对（不超范围、来源可追溯）
- [ ] PRD / ARCHITECTURE / ROADMAP 三件套定稿
- **验收**：系统在公司机房一键启动可用，试点一个真实项目

## 3. 任务优先级（P0/P1/P2）

| 优先级 | 任务 |
|---|---|
| **P0（必须）** | 结构化切块、混合检索+重排、需求提取、多候选生成、人工逐条选择、来源引用、Docker 部署 |
| **P1（重要）** | 元数据过滤、版本管理、增量索引、内容回流、超范围校验 |
| **P2（增强）** | 多用户权限、项目隔离、审计日志、检索质量评测工具 |

---

## 4. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 切块质量不佳 | 检索不准、生成差 | 用结构化切块 + 混合检索 + 重排，M4 专项调优并评测 |
| 需求提取漏项/错项 | 响应不完整 | 提取后人工确认环节兜底；用真实招标文件校准 |
| 生成超范围 | 合规风险 | 提示词强约束 + 超范围校验拦截 + 无来源内容标"待补充" |
| 知识库初始质量 | 检索结果差 | 入库前清洗、去重、标注元数据；试点项目校验 |
| 多候选同质化 | 人工挑选意义弱 | 生成时强制差异化（详略/角度/表述） |

---

## 5. 验收基线（与 PRD 对应）

- 需求提取：能从典型招标文件提取主要需求条目，人工可修正。
- 检索命中：对典型需求召回相关历史标书内容。
- 多候选：每条需求生成 3 个候选，均带来源引用。
- 超范围率：明显超范围内容占比低，可被校验拦截。
- 组装导出：按章节组装并导出 docx。
- 部署：系统在公司机房 / VM 一键启动可用。

---

## 6. 后续迭代方向（M6 之后）

- 检索质量评测体系常态化。
- 知识库按项目/团队/行业分域管理。
- 多候选生成策略增强（个性化、风格偏好记忆）。
- 与公司现有 OA / 文档系统集成。
