## 1. 主路径

```
上传招标文件 → 解析成功
  → ① 读标：模型输出三张清单（技术需求 / 评分规则 / 废标）
  → ② 拟目录：一次模型调用，1～4 级目录，每个节点挂响应要点
  → ③ 用户确认目录（唯一闸门；可改标题、增删要点）
  → ④ 开始生成：逐叶子节点 双库 RAG + 要点 + 废标约束 写正文
  → ⑤ 内置审核：废标约束检查 + 质量八条 → 覆盖视图标「需人工确认」
  → ⑥ 导出：服务方案正文 + 技术偏离表
```

## 2. 三张清单（workflow.tender_digest）

模型分块读标（沿用 `technical_model_extract` 的分块、超时与降级记账），每块输出 JSON，合并去重后编号。

| 清单 | 编号 | 字段 |
|---|---|---|
| 技术需求 | `T-01…` | text（≤40 字要点）、quote（原文短句）、page、file_id、star（★/实质性）|
| 评分规则 | `S-01…` | item（评分项）、score（分值，原文没有留空）、criteria（评分标准原文）、points[]（顿号/逗号拆出的得分要点）、quote、page |
| 废标 | `R-01…` | text、quote、page、category（技术/资格/商务/格式）|

- 三张清单同时写回 `requirements`（`requirement_type` = tech / scoring / rejection），覆盖视图、偏离表、约束检查继续用同一份数据。
- 无可用本地模型时，回落到现有正则抽取，并在页面上标明「规则抽取」。
- 禁止编造：原文没有的分值、期限、系统名一律留空。

## 3. 目录（technical_outline.headings）

一次模型调用输入三张清单（废标只作背景，不成章），输出：

```json
[{"level":1,"title":"服务内容"},
 {"level":2,"title":"健康检查","points":[{"text":"季度全面健康检查并出具报告","refs":["S-02","T-05"]}]}]
```

确定性校验（不再做大段修补）：

1. 层级 1～4，不跳级；标题是短章节名，不抄条款整段。
2. 每条 `S` 的得分要点、每条 `T` 至少挂一次；漏挂的自动补进「其他服务承诺」节，并在覆盖视图标出。
3. JSON 解析失败或校验失败：重试一次；再失败则用规则目录（评分要点→三级标题，技术需求按主题分组），并显示原因。

每个叶子节点就是一个 ResponseTask，记录 `points[]`、`requirement_ids[]`、`scoring_ids[]`。现有 1300 行修补逻辑只作规则回落使用。

## 4. 正文生成

每个叶子节点：

- 检索词：节标题 + 前 3 条要点短语（不放招标原文）。
- 检索：两个库各取一次后合并；历史标书降权外项目专名（沿用）；每节审计写进覆盖视图。
- Prompt 五块：本节要点（含关联评分标准）｜技术需求原文｜**全部废标清单（硬约束）**｜知识库片段（带引用标记）｜写作规则（理解要求 → 我方做法 → 步骤/工具/频次 → 产出物 → 结合本项目；不虚构；无依据写【待确认】）。
- 失败节保留兜底文本，可单节重试；会话可恢复（沿用）。

## 5. 覆盖视图（= 矩阵）

一行一个「要点」（S 的得分要点、T 的需求、R 的废标项）。

| 列 | 字段 | 说明 |
|---|---|---|
| 类型 | `kind` | 技术需求 / 评分规则 / 废标 |
| 要点 | `text`、`quote`、`source_page` | 悬停看原文，点击打开原文定位 |
| 分值 | `score` | 仅评分规则 |
| 目标章节 | `outline_number`、`outline_title`、`section_key` | 点击跳到编辑台对应节 |
| 生成状态 | `generation_status` | 未生成 / 生成中 / 已生成 / 生成失败（带「重试」按钮，单节重写）|
| 偏离 | `response_type` | 无 / 正 / 负偏离（技术需求；写入偏离表，可改）|
| 人工确认 | `confirm_status`、`confirm_reasons[]`、`confirmed_by/at` | 待确认原因：无知识库依据、负偏离、废标冲突、质量八条未过、生成失败兜底、漏挂补入；「标记已确认」按钮 |
| RAG 检索 | `rag` | 见下表 |
| 约束检查 | `constraint` | 废标行：通过 / 冲突（冲突句）|

`rag` 字段：

| 字段 | 含义 |
|---|---|
| `query` | 实际检索词 |
| `history_hits` / `material_hits` | 两库命中数 |
| `top[]` | 前 5 条：`dataset`、`name`、`score`、`snippet`（≤120 字）、`cited`（正文是否引用）|
| `status` | ok / empty（无命中）/ missing_dataset（库未配置）/ error |
| `error` | 失败原因 |
| `searched_at` | 检索时间 |

顶部统计：要点总数、已生成、失败、待人工确认、无依据、质量八条通过数。筛选：类型、状态、待确认。实时更新沿用生成会话的 `task.patched`。

新增接口（`/api/v1`）：

- `POST /projects/{id}/technical-volume/sections/{section_key}/retry`：单节重写，走同一会话流。
- `POST /projects/{id}/coverage/{row_id}/confirm`：标记或撤销人工确认（记录人和时间，写审计）。

## 6. 质量八条（内置审核清单）

保留现有 8 条（大纲覆盖与一一响应、评分得分点有实质段落、结合客户实际、目录层级 1～4 合理、开收与图文总结、措施可落到招标场景、规范书条款体现、扣住项目核心）。

- 输入改为三张清单与节要点。
- 结果按节落到覆盖视图的「人工确认」原因，也在编辑台节状态显示。
- 不挡内部稿导出。

## 7. 写作助手

现状缺口：技术分册「问答写作」只回固定文案，没有接后端；「标书修改」只能整章出候选；没有按节作用域、检索依据展示，也不做约束检查。

| 能力 | 设计 |
|---|---|
| 作用域 | 默认当前光标所在节；可切选区 / 整章 |
| 问答 | 接后端流式问答；上下文 = 本节要点 + 关联评分标准 + 废标清单 + 双库命中；回答带引用，可复制，可「转为修改指令」|
| 修改 | 指令 → 本节候选（流式）→ 差异预览 → 采纳写入（编辑锁 + If-Match）/ 放弃 |
| 写入前检查 | 候选先跑废标约束检查和数字一致性检查，有冲突时显示并要求确认 |
| 快捷指令 | 补齐未覆盖要点（来自覆盖视图）、按五步结构重写、扩写措施、统一承诺数字、重新检索后重写 |
| 联动 | 覆盖视图「去修改」→ 跳到编辑台对应节并预填指令 |
| 留痕 | 问答与修改记入本人本节会话 |
