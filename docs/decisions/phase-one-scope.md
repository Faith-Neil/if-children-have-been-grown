## 建议交付的结果

业务人员能从招标文件出发，核对要求和公司材料，生成并修改有来源的正文，完成检查，导出技术、商务两册Word。每条重要要求能找到原文，每项关键承诺能找到依据，每次修改能知道谁改了什么。

先用一个项目、一章技术正文跑通真实流程，再扩展分册。单章试点只证明这一段流程可用，不能算完整一期交付。

当前只有文档和四个静态演示页面。正式账号、数据保存、后台处理、真实模型与Word导出都尚未建立；已有61项主要是前端计划及维护任务，尚不覆盖完整后端和模型工作。业务范围明确后补齐对应实施任务，不把前端估算当完整项目工期。

## 一次完整的使用过程

1. 创建项目，选定所属公司和负责人。
2. 上传招标文件及补遗；系统整理条款，人核对冲突、遗漏和无法识别的内容。
3. 将每条要求对应到分册、章节与证明材料；这张对照表叫“响应矩阵”。
4. 确认人数、服务期和响应时间等事实与承诺，检查公司是否有能力兑现。
5. 人确认大纲与写作方案，再按章节生成；没有依据或无法自动解决的内容交给人处理。
6. 人工修改、保存草稿、提交新版本；AI建议先展示改动，再由人确认采用。
7. 分册复核、定稿、全文检查；要求、事实或材料变了，旧检查需要重新确认。
8. 分别导出Word及合标核对清单，由业务负责人完成后续正式递交。

## 必须交付、延后与人工处理

| 分类 | 建议内容 | 怎样证明完成 |
|---|---|---|
| 主流程 | 真实上传、解析、人工确认、要求对照、事实确认、章节生成/编辑、检查和Word输出 | 从合成招标包开始跑完整流程，重启后资料和进度仍在；导出文件可打开并核对 |
| 来源与完整性 | 条款可回到原文页码；关键要求不得遗漏或无处理记录；缺依据内容标待补 | 用独立标注的原文样本检查遗漏，不能只统计已抽出的条目是否正确 |
| 公司与权限 | 公司间数据互不可见，无权限人员无法读、改或导出 | 用两家公司和不同角色实际尝试访问，后台也要拦住 |
| 编辑与版本 | 同一章节同一时刻仅一人能写，草稿可恢复，提交有版本与操作记录 | 两个人同时操作、失去编辑权后继续保存、重复提交和重启都能得到正确结果 |
| 检查与输出有效性 | 正文、事实、证据、模板或规则变化后，旧检查不能作为当前文件的通过依据 | 分别改动这些内容，核对旧检查及旧递交文件的状态和下载权限 |
| 必要配套 | 一家试点公司的已确认资料、写作规则、提示词版本、Word模板；必要登录、任务进度和配置页面 | 从空环境按说明启动，基础资产可用，失败任务能恢复或明确重试 |
| 延后增强 | 实时共同编辑、批注会签、语义查重、自动回收最终标书、客观分自动计算、邮件短信、全文搜索、移动端及专项模板 | 登记在后续范围，不占一期主流程的完成判断 |
| 人在系统外完成 | 报价编制、合并分册、最终目录/页码/评审索引核对、签章装订和正式平台递交 | 输出明确核对清单，由业务负责人确认完成 |

检查规则按参考PRD §5.8.1中“一期完整、一期简化、二期”的标记实施；不把44条规则都算成一期完整实现。敏感字段如何在内部稿与递交版显示，按角色和场景补明确规则后实施。
