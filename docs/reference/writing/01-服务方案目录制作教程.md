# 服务方案目录制作教程

> 适用对象：技术人员（只写「服务方案」这一大标题下的内容）  
> 依据：融科智联《投标技术服务方案编写规范》（RK-20260730-SH）及案例截图  
> 目标：从招标文件、评分标准、技术规格书中提取要点，用一、二、三级标题搭出可得分的服务方案目录

---

## 1. 你只写什么

招标文件通常由「评标办法 / 服务需求 / 投标格式」等组成，配套还有一份「技术规格书」。

投标文件里技术侧真正要写的，往往就是一个大标题：**服务方案**（有的标书叫「技术方案」「技术服务方案」，本质一样）。

其余如业绩、企业资质、报价、偏离表等，多由商务填写。技术人员先认清边界：

| 类型 | 常见内容 | 谁写 |
|------|----------|------|
| 客观分 | 业绩金额、企业资质（如 OPN 会员） | 商务为主 |
| 主观分 | **服务方案**（及同类技术叙述） | **技术为主** |

目录做得对不对，直接决定主观分能不能拿到「优」（案例中服务方案满分档要求：内容全面、要点一一对应且有具体措施、设计合理、描述清晰）。

---

## 2. 做目录前先读四样东西

不要一上来就套旧模板。按下面顺序读完再列大纲：

1. **通读招标文件 + 技术规格书**  
   搞清项目要干什么、服务范围、数据库/产品类型、服务期限。
2. **区分「技术干货」和「技术公共部分」**  
   - 干货：健康检查、故障处理、巡检、升级、性能优化等与本项目强相关的内容  
   - 公共部分：质保、保密、培训、售后等套话区（也要响应，但目录位置靠后、篇幅可控）
3. **识别评分标准和技术规格书中的关键字**  
   评分表「详细评分规则」里的逗号/顿号列举，几乎都是三级标题的原材料。
4. **识别响应文件格式**  
   看招标要求的章节编号、是否必须按某模板目录、偏离表怎么填。页码可先标临时页码，合标后再统一改。

---

## 3. 目录从哪里「抽」出来

服务方案目录有两个主来源，必须**同时覆盖**：

```
评分标准（主观分条目 + 要点摘要）
        ↘
         服务方案目录（一、二、三级标题）
        ↗
技术规格书（★章节与条款树）
```

### 3.1 从评分标准抽（保证「得分点」都有标题）

以规范中的案例为例，技术评审表里主观分只有「服务方案」10 分，评分内容写明：

> 服务方案中应包含数据库（包含 Oracle 或 MySQL 或 GoldenDB）的**健康检查、故障处理、例行维护、升级支持、性能分析优化、补丁升级、配置调整**等。

操作方法：

1. 找到主观分那一行（本案例即「服务方案」）。
2. 把「评分内容 / 详细评分规则」里用顿号、逗号、分号拆开的名词，**原词抄成三级标题**。
3. 「优」档常写「要点一一对应且有具体措施」——目录里有独立小节，正文才写得下措施；目录缺一项，正文再好也容易被判不全面。

抽完后的三级标题示例（挂在「服务内容」下）：

```text
3.2 服务内容
  3.2.1 数据库（含 Oracle / MySQL / GoldenDB）
  3.2.2 故障处理
  3.2.3 例行维护
  3.2.4 升级支持
  3.2.5 性能分析优化
  3.2.6 补丁升级
  3.2.7 配置调整
```

另一类评分表会把技术方案拆成固定几块并逐项赋分，例如：

1. 日常维护管理方案  
2. 风险控制措施  
3. 数据保密措施  
4. 服务支撑人员的管理制度  
5. 支撑服务应急处理  

这时应把这 5 项**原样升为二级或三级标题**，保证「5 部分内容组成完整」——缺一块就直接丢那一项的分。

### 3.2 从技术规格书抽（保证「逐条响应、一一对应」）

技术规格书常见结构（案例导航栏）：

```text
★1 技术规范定义
★2 技术服务要求
   2.1 基本原则
   2.2 服务案例要求
   2.3 技术服务内容
       2.3.1 标准服务
       2.3.2 现场服务
   2.4 软件健康检查服务
       2.4.1～2.4.4 配置 / 日志 / 性能 / 数据备份检查
   2.5 软件产品安装和升级服务
   2.6 软件产品故障分析与诊断服务
   2.7 软件产品运行保障服务
   2.8 主动式服务
   2.9 创新能力
★3 技术服务质量管理与考核
```

映射原则（PPT 原话）：**逐条响应，一一对应**。

| 规格书条款 | 服务方案目录怎么落 |
|------------|-------------------|
| 2.3 技术服务内容（标准服务 / 现场服务） | 升为「技术服务方式」下的二级/三级，或并入「服务内容」开头 |
| 2.4～2.9 各类专项服务 | 在「服务内容」下各占一条三级标题（可接在评分点抽出的 3.2.1～3.2.7 之后，如 3.2.8 健康检查……） |
| ★3 质量管理与考核 | 独立二级标题「技术服务质量管理与考核」 |
| 合同保密、附件格式要求 | 单独小节响应，不要漏在「其他」里 |

规格书有编号的条款，目录里尽量能**对上编号或对上原词**，方便评委对照打勾。

## 4. 一、二、三级标题怎么用

### 4.1 层级分工

| 层级 | 作用 | 从哪里来 | 写法要点 |
|------|------|----------|----------|
| **一级** | 整章唯一大标题 | 投标格式要求 | 固定为「服务方案」（或招标规定的同义标题），技术人员只在这一章内展开 |
| **二级** | 评分块 / 规格书大章 | 评分因素、规格书 ★2★3、实施与保障类公共块 | 少而稳：服务方式、服务内容、质量管理、实施计划、应急、培训/知识转移等 |
| **三级** | 得分点 / 规格书条款 | 评分要点摘要中的顿号词、规格书 2.x.x | **尽量用招标原文关键词**，一条一事，便于「一一对应」 |

更深层级（四级）只在某一条服务特别长时用（例如健康检查下再拆配置/日志/性能/备份），不要为了看起来「细」而无意义拆层。

### 4.2 推荐骨架（可按项目改编号）

一级标题始终是「服务方案」。下面是一套把「评分点 + 规格书」收拢后的常用骨架：

```text
N  服务方案                          ← 一级（大标题）

N.1  技术服务方式                    ← 二级（来自规格书服务方式/原则）
N.1.1  标准服务
N.1.2  现场服务
N.1.3  主动式服务

N.2  服务内容                        ← 二级（评分要点 + 规格书 2.4～2.9 的主战场）
N.2.1  数据库（Oracle / MySQL / GoldenDB）…
N.2.2  故障处理
N.2.3  例行维护
N.2.4  升级支持
N.2.5  性能分析优化
N.2.6  补丁升级
N.2.7  配置调整
N.2.8  软件健康检查服务              ← 来自规格书 2.4
N.2.9  软件产品安装和升级服务        ← 来自规格书 2.5
N.2.10 软件产品故障分析与诊断服务    ← 来自规格书 2.6
N.2.11 软件产品运行保障服务          ← 来自规格书 2.7
N.2.12 …（规格书还有的专项继续顺延）

N.3  技术服务质量管理与考核          ← 二级（规格书 ★3）

N.4  服务实施计划                    ← 二级（进度类评分常考）
N.5  应急响应机制                    ← 二级（应急/支撑服务类评分常考）
N.6  知识转移 / 培训方案             ← 二级（公共部分，合同常要求）
```

若招标投标格式已经规定了「八、服务方案」下的固定二级目录（如项目概述、功能指标、总体设计、进度、质保、项目管理、培训、保密），则：

- **一级、二级标题名以招标格式为准**，不要擅自改名；  
- 把评分要点和技术规格书条款，**嵌进最贴近的二级之下做三级**；  
- 招标格式没有、但评分/规格书有的条目，在最相关二级下增补三级，并在偏离表说明「正偏离/无偏离」（尽量避免负偏离）。

### 4.3 标题命名四条规矩

1. **原词优先**：评分表写「性能分析优化」，标题就写「性能分析优化」，不要改成「性能调优实践分享」。  
2. **一条一事**：不要把「故障处理与例行维护」挤在同一个三级标题里——分开才方便写「具体措施」。  
3. **覆盖完整**：列完目录后，对照评分表逐项打勾、对照规格书目录逐条打勾，两边都要「有标题可挂」。  
4. **编号风格统一**：与招标要求的章节编号体系一致（有的用 1.1.1，有的用 一、（一）、1.），合标前不要混用两套。

## 5. 实操步骤（建议严格按序）

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1 | 通读招标文件 + 技术规格书 | 项目理解笔记 |
| 2 | 圈出评分表里所有主观分 / 技术方案类条目及「要点摘要」 | 得分点清单 |
| 3 | 导出或抄下技术规格书目录树（含★条款） | 规格书条款清单 |
| 4 | 按投标格式确定一级标题「服务方案」及已有二级框架 | 一级+二级骨架 |
| 5 | 将得分点清单落成三级标题（优先挂在「服务内容」下） | 评分驱动的三级 |
| 6 | 将规格书未覆盖条款继续落成三级（或并入已有三级下的四级） | 规格书驱动的三级 |
| 7 | 补公共块：进度、应急、培训、保密、质保等（看评分和合同） | 完整目录草稿 |
| 8 | 双清单勾选：评分全覆盖？规格书全覆盖？ | 定稿目录 |
| 9 | 用 Word/WPS 标题样式生成导航窗格，确认层级正确 | 可开写的目录 |

PPT 要求的概括：

1. 根据技术规格书和评分标准罗列投标文件技术部分大纲；  
2. 罗列时对评分标准合理分解；  
3. 罗列内容应覆盖完整个技术规格书；  
4. 再按「八股」方式逐条应答（正文写法见《02-技术标响应教程》）。

## 6. 完整示例对照（评分点 → 目录）

**评分要点原文（摘录）：**  
服务方案应包含数据库（Oracle 或 MySQL 或 GoldenDB）的健康检查、故障处理、例行维护、升级支持、性能分析优化、补丁升级、配置调整等。

**错误目录（丢分）：**

```text
3 服务方案
  3.1 总体思路
  3.2 运维服务介绍          ← 太粗，评委无法对「补丁升级」等逐条打勾
  3.3 售后承诺
```

**正确目录（可对「优」）：**

```text
3 服务方案
  3.1 技术服务方式
  3.2 服务内容
      3.2.1 数据库（含 Oracle / MySQL / GoldenDB）健康检查与运维对象说明
      3.2.2 故障处理
      3.2.3 例行维护
      3.2.4 升级支持
      3.2.5 性能分析优化
      3.2.6 补丁升级
      3.2.7 配置调整
      3.2.8 …（规格书专项继续）
  3.3 技术服务质量管理与考核
  3.4 服务实施计划
  3.5 应急响应机制
  3.6 知识转移
```

左边规格书条款用红线「一一对应」到右边三级标题——目录阶段就把评委的对照表画好。

## 7. 目录阶段自检清单

- [ ] 大标题是否就是招标要求的「服务方案」（或同义规定标题）  
- [ ] 评分表主观分每一条「要点」是否都有独立三级（或明确四级）标题  
- [ ] 技术规格书每个需响应的条款是否都能在目录中找到落点  
- [ ] 二级是否过碎或过粗（一般 4～8 个二级较稳）  
- [ ] 标题用词是否与招标原文一致（便于检索、对照）  
- [ ] 数据库/产品类型是否在标题或首节就与招标范围一致（Oracle / MySQL / GoldenDB 等）  
- [ ] 进度、应急、培训、保密等公共块是否按评分/合同需要具备  
- [ ] Word 导航窗格层级是否正确（勿用手工加粗冒充标题样式）
