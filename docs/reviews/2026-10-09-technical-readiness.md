## 2. 需要在真实接入前收敛的合同

### TR-01 · P0：前后端缺少一个共同、可验证的契约基线

**触发与后果。** 前端按当前架构建立请求层，后端按 xqr 的 KB 代理草案实现，双方将分别决定公司条件、对象 ID、段落标识、版本、错误及任务状态。页面即使能够请求成功，也可能把错误公司的对象或旧版本结果当成可写内容；SDK、模拟数据和后台真实响应随后各自演变。

**证据。** [前端架构](../ARCHITECTURE.md) §5、§6.1、§8、§14 只有原则与示意字段；[FE-M0-T04/T08](../tasks/FE-M0.md) 将核心契约和 OpenAPI 列为待确认输入。`origin/xqr:docs/ARCHITECTURE.md` §7 仅列 KB 创建/上传/解析/切块/元数据/检索代理端点，未提供编辑、任务、导出的请求/响应定义。当前 `spec/openapi/` 不存在。前端示意 `paragraph_id` 与参考字典的 `paragraph_key`/`target_paragraph_keys` 需要明确映射。

**建议合同。** 首批只评审身份/当前公司、项目可见性、章节读取、锁、草稿提交和任务查询；在其中统一稳定 ID、段落结构、时间格式、业务状态代码、请求标识和可重复提交的操作标识。由服务端确定用户及公司上下文，客户端传的 `company_id` 不作为授权依据。约定会话失效、无权限、对象不存在、版本冲突、失锁和业务门禁失败的不同响应，明确哪些请求允许重试。HTTP 合同以 `spec/openapi` 为权威；生成 SDK 及模拟处理器，手写业务 hooks 留在应用中。

**验收。** 同一份合成样例分别通过 schema/模拟接口和真实实现验证；修改字段或枚举时能检测破坏性差异；403、旧版本、失锁、重放和另一公司对象均有实际拒绝用例。公司隔离不能仅通过菜单隐藏证明。现状分类：**缺正式契约设计，同时缺实现**。

### TR-02 · P0：租约失效、接管和写入必须在服务端构成同一个一致性边界

**触发与后果。** A 持锁后断网，B 接管；A 的延迟心跳、自动保存或先前打开的 Diff 再到达。若服务端只在打开页面时检查锁，或先检查再无条件保存，A 仍可覆盖 B 的内容。仅禁用按钮无法防止旧请求、其他客户端或后台写入。

**证据。** [前端架构](../ARCHITECTURE.md) §9 规定心跳/超时/接管，却未给租约身份和并发写入协议；[参考 PRD](../reference/product/prd-mvp-v1.8.md) §5.11.9 定义章节级独占、接管原因与草稿保护；[字典](../reference/product/kb-data-dictionary-v1.9.md) §3.10.4.6 定义每次取得一条 `edit_lock`、`expires_at`、`heartbeat_at`、`released_at` 及每章仅一个有效锁的逻辑约束。[FE-M3-T04](../tasks/FE-M3.md) 已登记双会话验收。原型 `app.js` 的 `ensureEditable()` 只检查本页面 `contentEditable`，不代表真实租约。

**建议合同。** 取得、续期、释放、接管均返回/携带本次 `lock_id` 或等效租约标记；旧租约不能刷新新锁。每次写入以服务端时间检查有效锁、持有人/会话、公司/项目、章节权限、分册定稿状态和预期版本，并将检查与写入放在同一事务或等效原子边界。接管顺序明确为保存已收到的原持有人草稿/记录失败事实、释放旧租约、创建新租约、发通知；断网客户端尚未上传的内容不能被宣称已自动提交，应保留恢复/对比途径。按最终数据库实现有效锁唯一性，不能把字典的“部分唯一”说明直接当成可执行迁移。

**验收。** 双会话同时取得锁最多一个成功；接管后旧心跳、旧草稿保存、旧 Diff、旧释放都被拒绝且不破坏新锁；无理由/无权限不能接管；失锁草稿有明确恢复记录；定稿章节通过任何写入入口都不能修改。现状分类：**租约/事务设计缺失；服务端实现缺失；已有原型防护验收只覆盖客户端**。

### TR-03 · P0：草稿、AI 建议和正式版本的提交结果必须可重放、可追溯

**触发与后果。** 两次自动保存乱序到达会让旧草稿覆盖新草稿；用户在生成建议后手改正文，旧建议可能写入错误段落；确认写入已成功但响应丢失，重试可能产生两个版本或重复插入。章节内容、引用、编辑记录和增量复查若分别落库，还可能出现“新版本存在但来源/任务缺失”。

**证据。** [前端架构](../ARCHITECTURE.md) §10～11 已区分草稿与正式版本；[参考 PRD](../reference/product/prd-mvp-v1.8.md) §5.11.6 要求先提交本人手改草稿、再核对选区，唯一重新定位时再次展示 Diff，歧义则拒绝；[字典](../reference/product/kb-data-dictionary-v1.9.md) §3.9.3～3.9.5 已有 `base_version_id`、`selection_hash`、目标段落、结果版本、差异快照和草稿状态。尚无自动保存乱序、提交幂等和副作用原子性合同。

**建议合同。** 草稿保存带服务端草稿修订号/预期修订号，拒绝旧修订覆盖；正式提交带预期章节版本和唯一操作标识，同一操作重试返回同一结果，操作标识与不同请求内容组合应报冲突。AI 采纳绑定实际 `suggestion_id`、选区快照、段落键、基础版本及用户确认的 Diff；重定位后先返回新差异和待确认结果，不能直接落正文。一次采纳的内容、来源/citation、编辑记录、样例状态和复查任务须一致提交，或有可靠且可补偿的持久化事件保证；回退生成新版本，保留旧版本和来源。

**验收。** 延迟旧自动保存、重复提交、提交后响应丢失再重试、唯一/多处/消失的选区、采纳中途失败、旧检查结果晚到均有真实用例；未修改段落逐字不变；草稿保存不生成正式版本。同一采纳只有一个正式结果，复查结果绑定该结果版本。现状分类：**参考业务设计较完整，缺协议/事务细化及实现**。

原型仍存在另一个明确的演示差距：`app.js` 的确认处理器固定修改 `.selected-demo p`，所有 `.show-diff` 打开同一静态 Diff，Toast 固定宣称 V9 而 `index.html` 顶部仍显示 V8。这是当前原型问题，可另开小任务修正上下文和显示一致性；它不是生产版本机制已实现的证据，也不需要借机重写框架。

### TR-04 · P1：解析、生成、检查、导出的任务结果缺持久化生命周期合同

**触发与后果。** 用户离开页面、事件连接断开、进程重启，或取消后任务才返回。只靠页面定时器/轮询文本会丢任务、重复启动、回退进度，甚至把取消的旧结果发布成当前结果。解析重试如果没有输入文件和处理步骤的稳定身份，还会覆盖补遗或重复创建要求。

**证据。** [前端架构](../ARCHITECTURE.md) §8 为 `queued/running/succeeded/failed`；[字典](../reference/product/kb-data-dictionary-v1.9.md) §4.16 的 `job_status`、`parse_job_status`、`generation_task_status` 为 `queued/running/completed/failed/cancelled`。这需要合同映射，不能直接任意改数据库代码。[参考 PRD](../reference/product/prd-mvp-v1.8.md) §5.12.4 要求恢复任务、失败步骤重试、取消、实时重连、权限裁剪和 `job` 为事实源；字典 §3.10.7.10 已有进度、业务对象关联和重试来源。xqr 架构 §7 仅提解析异步轮询；没有事件/重试/取消合同或 worker 实现。

**建议合同。** 启动返回稳定 `job_id`，查询返回权威快照、业务对象/输入版本、步骤、进度单位、状态修订、结果引用和允许操作。选用轮询或事件流后定义断线恢复、去重/顺序、快照校准和终态规则；如用 SSE，再明确事件 ID 与重连位置。重试记录原任务和失败步骤，定义能否复用已完成产物；取消区分“请求已接受”与“已停止且结果不发布”。结果写入前再核对取消状态和输入版本；不要依赖浏览器保持连接。解析合同同时保留文件版本、页码/坐标、块 ID、提取版本和人工确认版本，确认门在服务端核验冲突、疑似遗漏及逐条确认条件。

**验收。** 刷新/离开后恢复同一任务；断线/重复/乱序事件不能把完成回退为运行；进程重启可恢复或明确失败；取消与完成竞态只有一个可解释结果；同一输入重放不重复建业务结果；失败步骤重试不覆盖已人工确认的新数据。平台任务视图按 PRD §5.12.4 脱敏且不能重试/取消公司任务。现状分类：**业务状态已有，缺恢复/幂等/取消/事件协议；实现缺失**。

### TR-05 · P0：检索、AI 路由和附件访问必须共用公司/资源授权边界

**触发与后果。** 客户端篡改项目/数据集/附件 ID，或后台检索只使用 RAGFlow 服务 key 而未附正确公司和受限资料权限，其他公司或已撤销权限的资料可能进入回答、来源卡、日志或导出。敏感项目失败后自动改用云端模型也可能越过既定路由边界。

**证据。** [前端架构](../ARCHITECTURE.md) §12 明确服务端最终授权；[参考 PRD](../reference/product/prd-mvp-v1.8.md) §8.1 和[字典](../reference/product/kb-data-dictionary-v1.9.md) §1.7 要求服务端强制公司条件、项目/资源权限；PRD §6.5 定义强制本地与降级，§5.11.15 定义资料库/本项目答案卡及知识库关闭时的查询边界。xqr PRD §5 将角色/项目隔离列为可选，§7 排除外部云；xqr 架构 §7/§8 虽写服务 key 仅后端、检索只读，却没有这些公司权限和路由细节。不同方案的范围尚未冻结。

**建议合同。** 每个读写、检索、任务、缓存、来源回查、附件下载均在服务端绑定身份与公司，再核对项目/资源可见性。检索过滤不能由客户端任意传入或关闭；返回引用须在本次授权检索/直查快照内。权限撤销后的缓存、建议采纳和下载应重新校验；调用日志记录路由/模型/输入类别并按规定脱敏。敏感项目只用允许的本地服务，失败就排队/失败，不自动云降级。先确认云端是否纳入合作交付范围再实现其通路。知识库关闭时，资料库查询和本项目直查分别处理；普通问答不直接写正文或权威资料库。

**验收。** 两家公司同构 ID、篡改 project/dataset/attachment、撤销受限资料授权、同用户换项目、敏感项目本地不可用等真实用例均无越界数据；AI 请求与返回来源可核对；关闭知识库时不查公司资料，但按已确认意图规则可查有权本项目数据。现状分类：**参考已有强制规则，合作系统草稿存在范围差异；统一设计和实现均未完成**。

### TR-06 · P0：导出许可、检查版本和文件内容需要绑定同一批次快照

**触发与后果。** 全文检查通过后正文/事实/模板被改，用户仍按旧检查导出；分册在生成文件期间被解锁；下载接口只认文件 ID 而不重新授权；内部稿沿用递交版解密逻辑。这会产生未经当前检查的文件或扩大完整敏感字段的可见范围。

**证据。** [前端 PRD](../PRD.md) §23～25 已区分分册定稿、内部稿/递交版和外部合标，但规则较简；[参考 PRD](../reference/product/prd-mvp-v1.8.md) §5.9.1 明确递交版只由项目负责人导出、全部系统分册已定稿且全文检查有效、内部稿始终掩码、完整值仅填已确认要求的位置、修改/解锁后过期。字典 §3.10.6.1 有 `content_version_hash`、`compliance_run_id`、批次及 `full_value_fields`；[FE-M4-T03～T06](../tasks/FE-M4.md) 已把这些列入待实施验收。xqr PRD §7 又排除商务标和资质文件，需先解决范围差异。当前没有导出服务、模板实现或实际输出样本。

**建议合同。** 创建导出任务时以服务端核对角色/项目、导出类型、定稿/检查状态及所用章节/事实/证据/模板/规则版本，形成可追溯输入快照与批次；明确生成途中版本改变时继续生成历史快照还是作废，历史文件不可再显示为当前有效递交版。内部稿和递交版分别控制解密字段/位置及审计，不能以客户端传入的 `full_value_fields` 任意扩权。下载时再次检查公司/项目权限、文件归属和有效状态；签名链接策略、存续期限和已过期文件查看规则应明确。各系统分册分别出 Word 与合标核对清单，不自行扩成系统内合标。

**验收。** 检查后改文/解锁、导出途中更新、伪造角色/字段范围、跨公司文件下载、过期文件及重试均有真实用例；输出可追到同一内容/检查/模板批次。实际打开代表性 Word 样本核对标题、目录、分页、扫描附件范围、水印、暗标属性与掩码，界面“下载成功”不能代替文件验收。现状分类：**参考业务规则已有，缺快照/下载/事务合同；实现缺失**。

## 3. 图片目录与已写目录方案的渐进调整

图片提供目标候选；实际基线采用 [repository-layout](../architecture/repository-layout.md) 的“首轮整理快照”和“后续目标结构”，并结合 [DOCUMENT_INDEX](../DOCUMENT_INDEX.md) 核对后来新增的治理资产。目录方案当前明确“随对应功能开始实现再建立”，这个原则应继续保留。下表提出目录职责选择，暂不执行迁移。

| 图片路径 | 实际/已有方案 | 渐进处理与建立条件 |

## 4. 后续最小推进与退出条件

1. **先完成 FE-M0-T03/T04 的范围与合同评审。** 保全 xqr 系统方案与当前前端方案，确认技术/商务分册、云调用、公司隔离、生成方式和责任方；取得或经评审替代缺失的技术方案/设计基线。以 TR-01～TR-06 的合同与验收关闭具体差异，不以治理版本号相同替代语义对齐。
2. **建立一个可运行的真实切片。** 以两家合成公司、一个项目及章节为最小数据，跑通身份/公司过滤、章节读取、取得锁、草稿保存、提交新版本和审计。验收延迟旧请求、接管和重试。首批迁移、API、SDK、模拟数据与集成测试一致后，才把相应前端接入任务转 ready；不一次搭出图片全部空目录。
3. **随后接一个真实可恢复的解析任务。** 串联上传文件版本、任务快照/事件或轮询、可定位结果、服务端确认门；验收断线、重启、取消、失败步骤重试及人工确认后重跑。AI 适配以同样任务/权限边界接入，生成不直接发布正文。
4. **最后贯通检查与 Word 输出。** 先明确版本/规则/模板快照与导出授权，再用实际文件验证内部稿掩码、递交字段范围、分册与过期行为。部署形态由这条实际链路的依赖和运维环境决定。

以上为建议验收次序，不改写现有 FE 里程碑完成事实。当前静态原型可以继续做上下文/Diff/版本显示的小修；各生产合同均需要后端提供方与前端共同确认。本报告只新增审查输入，任务验收、索引登记和路径提升由根维护任务统一处理。本轮已新增来源清单及工作区同步工具，第三节目录表仍说明首次评审基线与目标职责，不将这些工程工具称为业务实现。
