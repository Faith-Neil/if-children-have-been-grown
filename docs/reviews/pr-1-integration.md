## 5. 建议整合方式

1. 保全 main 的前端三件套、UI/UX 规范与静态原型。
2. 将 xqr 的系统三件套放入独立系统区域（例如 `docs/system/`），并明确它们是待核对的系统方案；不得覆盖 main 的前端三件套。
3. 将“目录迁移与引用更新”和“技术选型采纳”分开处理。目录迁移不代表批准 RAGFlow、MySQL 或其他选型。
4. 在文档索引中记录各文件的层级、来源提交、状态和后续维护职责。
5. 适配治理规则后，再评审是否保留 Issue、交付记录与治理文件。
6. 通过独立整合变更处理两分支，保留清楚的来源与路径对照，供协作者迁移后续改动。

目录调整需检查根 README、文档索引、原型 README、Issue 与交付说明，以及 `.cursor/rules/` 中的硬编码路径。原型 `index.html` 使用同目录的 `app.js` 和 `styles.css`；整体搬迁原型目录时应保留这三者的相对关系。

## 7. 本次未合并原因

PR #1 的三件套与 main 使用相同路径，实际却描述系统与前端两个层级；普通覆盖式合并会造成内容丢失。治理规则还带有采购合同审核产品的路径和缺失测试规则引用，需要适配。

同时，xqr 的存储选型虽有分支内部记录，但本次目录整理没有重新验证其适用性。先形成可审查的文档分层与路径对照，再决定技术方案及治理文件的采纳范围，能够保全双方已有工作。

本次只新增本评审文档，不复制分支方案、不改变技术冻结、不修改 PR、不提交 Git 变更。
