为什么有这个文件：按 2026-11-20 用户要求，核对各权限账号能看到的功能是否仍是空壳、是否重复、是否有效。

它解决什么问题：给技术服务方案精简主路径之外的模块一个"保留 / 合并 / 补实"的依据，不删不藏。

# 角色与功能审计（2026-11-20，分支 feat/iss-047-technical-volume-mvp）

依据：代码静态核对（`project_access.py`、`session_navigation.py`、`shared/roles.ts`、`GlobalPagesContent.tsx`、`ProjectWorkspaceContent.tsx`、各页面数据来源）。未在浏览器逐账号点验。

## 1. 账号与角色

用户确认（2026-11-20）：只有 3 个登录角色——平台管理员、公司管理员、用户。平台管理员可创建公司管理员和用户并分配到公司；公司管理员只能创建本公司用户。只读按**项目角色** `readonly` 区分，不设只读登录角色。

代码现状：后端 `project_access.py` 和前端 `shared/roles.ts`、用户管理页可分配角色与上述一致。

| 演示账号 | 名义 | 实际 | 问题 |
|---|---|---|---|
| admin、platform-admin | 平台管理员 | 平台管理员 | 正常 |
| alpha-company-admin | 公司管理员 | 公司管理员 | 正常 |
| alpha-manager / editor / tech / business、beta-* | 项目经理 / 编写人 | 用户 | 名称误导，权限正确 |
| alpha-viewer、alpha-auditor | 查看人 / 审核人 | 用户（可写） | 名称误导；要只读须在项目里设为 `readonly` |
| alpha-data-admin | 资料管理员 | 用户 | 名称误导；受限证据可见性仍认 `data_admin` 原值，与三角色不一致 |
| alpha-group-admin | 集团管理员 | 用户，公司为 group | 无对应角色，进不了项目 |

## 4. 建议（不删不藏）

| 问题 | 建议 |
|---|---|
| 演示账号名称误导 | 演示种子账号改为三角色命名；只读演示改为项目内 `readonly` 成员 |
| 残留旧角色判断 | 清掉 `data_admin` 原值判断与空的只读登录角色分支，统一走三角色 + 项目角色 |
| 项目只读 | 确认 `readonly` 项目成员在后端所有写接口（含写作助手、生成、重试、人工确认）都被拒 |
| 写作档案空壳 | 接后端存储，并把自称口径、禁用词注入正文生成和写作助手检查；在那之前页面标"样例" |
| 方案片段孤儿页 | 作为知识库页的一个页签挂回去，或明确并入资料库数据集 |
| 任务页与抽屉重复 | 保留抽屉做快速查看，任务页做完整历史，两者共用一个数据源与组件 |
| 死入口 | 后端不再下发没有页面的入口，或补页面 |
| 矩阵 / 覆盖视图重复 | 按设计 §5 合一：覆盖视图为主表，SLA 与证据作为行详情 |
