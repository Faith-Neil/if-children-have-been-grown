## 1. 核心产品验收点逐项核实

### 1.1 正式 Token 凭据登录与 8 角色权限（企业级产品感）
- **PRD 对照**：§2.2、§2.3、§5.12.1；PRD 缺口 P0-2、P1-1。
- **核实结果**：
  - **关演示安全门禁**：在生产配置（`ICG_ALLOW_DEMO_LOGIN=0` / `VITE_DEMO=0`）下，旧演示登录端点 `/api/demo/login` 严格阻断（HTTP 403 `FORBIDDEN`，附带 `Deprecation: true` 标记），杜绝内置演示账号后门；
  - **正式 Token 会话鉴权**：系统支持标准 Bearer 凭据认证，`GET /api/v1/session` 返回规范的 `auth_mode="authenticated"` 与 `role_mode="rbac-8roles"`；
  - **8 角色 RBAC 细粒度控制**：
    - `project_lead` 与 `company_admin` 享有项目创建与全局推进权限（包含 `projects.create`、`library.write` 等）；
    - `bid_writer` 严禁越权新建项目（实测 `POST /api/v1/projects` 严格拦截返回 HTTP 403 `PROJECT_CREATE_FORBIDDEN`），仅保留正文编写、锁申请与证据挂接权限；
    - `auditor`、`viewer` 保持严格的只读审查权限；
    - `group_admin`、`platform_admin` 具备集团与平台专属管理路由；
  - 彻底摆脱了过去“仅能演示三角色”的玩具感，展现出真实企业级多角色分权协作形态。
- **验收结论**：**通过**。

### 1.2 主流程六大阶段真实可演示性（关演示模式）
- **PRD 对照**：§4.2 主流程验收表（新建项目 → 招标文件解析 → 响应矩阵 → 资料证据 → 分节生成/编辑 → 检查与导出）。
- **核实结果**：
  - **阶段 1：项目创建与团队分工**：前端入口调用对齐至规范的 `POST /api/v1/projects`，支持 `Idempotency-Key` 幂等防重与团队成员、分册负责人配置；
  - **阶段 2：招标文件上传与解析确认**：支持 Base64 文件上传与异步解析；在未完成条款与事实确认前，提前触发 confirm 会被严格阻断（HTTP 409 `REVIEW_PENDING`），待核对后方可确认；
  - **阶段 3：响应矩阵与证据库挂接**：在资料库中正式录入资质证据，矩阵行精准映射分册章节，录入响应并挂接已确认证据；
  - **阶段 4：大纲方案确认与章节生成**：支持确认章节方案（`POST /plan`），触发初始内容生成（`POST /generate`）；
  - **阶段 5：编辑版本提交与锁生命周期**：章节支持获取编辑锁（`/lock`）→ 提交新版本（`/versions`）→ 释放锁（`/lock/release`），生成内容真实落地；
  - **阶段 6：检查与导出**：合规检查成功核对要求项、事实与分册正文，形成检查批次。
- **验收结论**：**通过**。

### 1.3 诚实门禁与合规警示（杜绝虚假放行与糊弄验收）
- **PRD 对照**：§5.8.5、§5.9.1；Gap 总结 P0-1。
- **核实结果**：
  - **红线强阻断**：若存在未解决的废标或星号条款阻断缺陷，正式递交导出（`kind="submission"`）强拦截返回 HTTP 400 `CHECK_BLOCKER_EXISTS`；
  - **定稿不全底线拦截**：即使 blocker 已清零，由于当前分册定稿与 R01~R44 规则体系未完全落地，递交导出严格阻断返回 HTTP 409 `RULES_INCOMPLETE`（“完整合规规则与分册定稿未实现，不能把本地内部稿冒充递交版”），坚决不虚假放行；
  - **内部评审放行与合规告警**：内部评审稿（`kind="internal_review"`）放行（HTTP 200），但快照强制打标 `has_blockers=True`，并挂载醒目的 `compliance_notice="存在未解决的废标或星号条款阻断项，仅供内部评审，不可作为正式递交文件。"`；无 blocker 内部稿则提示 `"仅供内部评审，不可作为正式递交文件。"`。
- **验收结论**：**通过**。

### 1.4 导出文件格式合法性与防篡改溯源
- **PRD 对照**：§5.9.1、§5.9.3；BE-M0-T15 版式标准。
- **核实结果**：
  - 下载接口返回标准 Word 媒体类型 `application/vnd.openxmlformats-officedocument.wordprocessingml.document`；
  - 二进制压缩包解包核验包含合法的 `[Content_Types].xml` 与 `word/document.xml`，正文与标题均正确封装；
  - 整本与分册均注入 64 位 SHA-256 十六进制内容指纹及 Word 默认版式元数据（A4 纵向、标准页边距、行间距 28pt、首行缩进 560 缇、一级标题居中黑体等），满足防篡改与排版合规需求。
- **验收结论**：**通过**。

## 3. 后续里程碑与第二阶段（APP-M2 / PRD P0）派工建议

本任务的顺利完成标志着系统具备了**真实可演示、企业级多角色分权、关演示安全可闭环**的扎实底座。针对目前与 PRD MVP v1.8 最终上线形态之间客观存在的深度功能缺口，建议在第二阶段重点派发以下产品需求：

1. **【P0-定稿闸门产品化】（对应 PRD §5.8.5 与 Gap P0-5）**：
   - 落地「分册检查 → 交叉复核确认 → 分册定稿锁定 → 全文检查」完整状态机；
   - 增加分册锁定（冻结编辑）与交叉复核人员通读签字留痕体验，使分册状态流转至“已定稿”，打通合法解除 `RULES_INCOMPLETE` 的正规路径。
2. **【P0-合规规则最小可递交集落地】（对应 PRD §5.8.1 与 Gap P0-1）**：
   - 按 PRD ● 级项优先实现第一批关键规则（R15 证明材料齐全、R23 星号废标全响应、R09/R10 SLA 与金额承诺、R34 占位符清零、R36 跨分册人员一致性、R37 偏离表一致性）；
   - 将现有工程门禁对齐至 R01~R44 编号体系与检查问题列表界面。
3. **【P1-知识库与方案片段界面接通】（对应 PRD §5.5 与 Gap P0-4）**：
   - 将前端导航中的 `knowledge` 从 `PendingPage` 替换为方案片段管理与发布页；
   - 接通后端已有的 `snippet_publication` API 与 RAG 检索，实现历史片段的真实录入与引用。
4. **【P1-编辑台对话助手答案卡交互闭环】（对应 PRD §5.11 与 Gap P1-3 / Q27）**：
   - 在前端编辑台侧栏实现 Q27 结构化答案卡呈现与 3~5 条修改样例插入；
   - 提供知识库开关对检索范围的直观控制与引用来源卡片展示。
