为什么有这个文件：解释后端demo的实际运行过程，以及以后怎样接入模型和数据库。

它解决什么问题：让接手者了解权限、编辑和输出由哪里控制，避免替换接口时破坏已验证的约束。

# BE-M0-T01：后端代码解释

日期：2026-10-10。关联：[ISSUE-006](../../issues/ISSUE-006.md)、[任务](../tasks/BE-M0.md#be-m0-t01)、[交付](../delivery/BE-M0-T01.md)。

## 一次操作怎样到达后台

1. [页面](../../backend/bid-core/icg_demo/static/index.html)显示账号、技术/商务章节、正文与操作结果。
2. [页面脚本](../../backend/bid-core/icg_demo/static/app.js)把操作送到后台；登录凭据只留在当前页面内存，切账号或章节清掉旧编辑凭证、建议和检查状态。
3. [HTTP入口](../../backend/bid-core/icg_demo/main.py)核对请求字段与账号，统一错误与请求编号。
4. [业务核心](../../backend/bid-core/icg_demo/domain.py)按公司、角色、当前编辑凭证和正文版本决定是否允许操作。
5. [内存仓库](../../backend/bid-core/icg_demo/adapters.py)在同一事务中保存正文、版本、操作记录与重复请求结果。事务是“一组变动要么一起成功、要么一起撤回”。
6. 页面展示后台结果；检查通过后可以下载后台实际生成的Word。

## 两个可替换位置

[ports.py](../../backend/bid-core/icg_demo/ports.py)定义两种能力的约定：

- `Repository.read()`返回隔离的数据快照，`transaction(operation)`在一次原子操作中提交结果；当前`MemoryRepository`使用单进程互斥锁和副本，异常不会留下半份改动。真实数据库要保留公司筛选、事务回滚、版本比较和重复请求唯一性。
- `ModelProvider.suggest(instruction, content)`根据修改要求与正文返回建议。当前`DemoModelProvider`确定性返回演示文本，没有网络调用。真实模型在这里替换，并另做超时、敏感资料路由和来源检查。

`create_app(repository=..., model_provider=..., clock=...)`注入实现。实际测试已经替换模型和仓库，验证它们被调用以及故障回滚；预留接口不是一个空文件名。

## 编辑与保存为何不会相互覆盖

每个编辑凭证绑定账号、登录会话和120秒有效期。经理接管需理由，并使旧凭证失效；每次保存、续期和释放都重新核对，不能靠页面按钮决定是否有权。

草稿带正式正文的基础版本和递增序号，旧请求不能覆盖较新的草稿。提交正文同时生成新版本、操作记录和重复请求结果；同一请求重试只返回第一次结果，改变内容却沿用同一标记会被拒。

页面每30秒续期；失去编辑权后关闭写入操作。模型建议只展示文本，采用到编辑框后仍要人工提交。这里没有完整富文本编辑器或视觉差异比较，原静态原型保持独立。

章节打开时先显示最新已提交正文，本人草稿单独保留在只读区。草稿的基础版本落后时阻止编辑与提交；用户明确核对最新正文后才能继续或恢复。恢复先复查当前版本，再按该版本保存新草稿，保存成功后才替换编辑框，避免把旧草稿悄悄套用新版本号覆盖他人的修改。同账号另一次登录看到的锁摘要不等于本会话取得了编辑权。

## 检查和Word的实际边界

基础检查拒绝空正文和包含“待补”的文字，不理解上下文，不代表完整业务规则。检查记录绑定已提交正文版本和内容摘要；摘要是用来判断内容是否变化的指纹。

草稿不进Word，也不改变已提交版本的检查。提交新版本后，旧检查不能创建新输出，旧文件下载也被拒。Word由标准ZIP/XML结构生成，含单章段落与演示内部稿标识；下载再次核对公司和版本。
