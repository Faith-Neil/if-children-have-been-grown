- 日期：2026-10-12。代码：`backend/bid-core/icg_demo/ports.py`、`backend/bid-core/icg_demo/retrieval.py`。PR：未创建。

## 改了什么以及为什么

原来只有仓库、对话模型和解析器三个替换口。向量库还没选定，业务库虽已定为 MySQL 8，但 MySQL 8 没有向量检索。本次只增加嵌入、重排和向量检索的协议，以及一个不进入 HTTP 的证据候选服务，避免后续实现直接绑到某一种库，或把历史投标写成可附着证据。

## 入口和调用顺序

协议在 `ports.py`。`EmbeddingProvider.embed` 接收字符串列表并返回同样数量的向量。`RerankProvider.rerank` 接收查询和文档列表，返回每个文档下标一次，靠前的更相关。`VectorStore.upsert` 按 id 覆盖。`VectorStore.search` 必须同时给出 `company_id`、`status` 和 `type`。

内存实现和 `EvidenceCandidateService.collect` 在 `retrieval.py`。`create_app` 不构造这个服务，现有页面和 `test_reference_boundaries.py` 的请求路径不变。

调用顺序：

1. 路径 A 只看同一公司、状态为 `confirmed`、类型不是 `history` 的资料，并要求查询是名称加正文的子串。结果可附着，不是仅供参考。
2. 知识库关闭时直接返回路径 A，并记下 B、C 的原因是 `knowledge base is off`，此时不调用嵌入。
3. 路径 B 嵌入全部片段、写入向量表、再按本公司、`confirmed` 和类型 `chunk` 搜索，然后重排。结果可附着。
4. 路径 C 只保留同一公司的历史投标，`attachable` 为 false，`reference_only` 为 true。
5. B 或 C 抛出异常时丢掉该路径，保留其余路径。原因只写路径和异常类型名，不写异常消息，因此资料正文不会进原因。

## 数据与状态

向量表是进程内字典。嵌入把文本压成 32 维字块计数，再做归一化。它不是嵌入模型，也不访问网络。重排按共有字块计数，分数相同则保持原顺序。搜索用余弦相似度，相同分数再按 id 排序。

请求里的资料、片段和历史投标由调用方传入。服务不读现有内存仓库，也不写项目、章节或证据表。测试使用 `company-alpha`、`company-beta` 和查询“机房巡检”。

## 关键判断与异常

搜索缺少公司、状态或类型时拒绝。返回结果若越出这三个条件，路径 B 失败。重排若漏掉或重复下标，路径 B 也失败。公司编号为空白时，整个收集拒绝，不产出候选。路径 A 自身的失败不被捕获，因为它是回退目标。
