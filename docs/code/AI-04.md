# AI-04：CI 假 RAGFlow 检索服务

- 对应任务 [AI-04](../tasks/AI-M0.md#ai-04)、[ISSUE-037](../../issues/ISSUE-037.md)、[交付](../delivery/AI-04.md)。
- 日期：2026-10-13。代码只在 `tests/backend/` 与 `pytest.ini`。不改 `backend/bid-core`。PR：未创建。

## 改了什么以及为什么

托管 CI 没有 RAGFlow 密钥，也到不了内网。`FakeRagflow` 用标准库在 `127.0.0.1` 的临时端口上接受 `POST /api/v1/retrieval`，并提供 `GET /api/v1/system/healthz`。它把收到的请求头原样记下，并把路径末尾的 `/api/v1/retrieval` 或 `/api/v1/system/healthz` 去掉，得到调用方实际使用的 `base_url`。带 `/gateway` 这类前缀时，前缀留在 `base_url` 里。

检索成功体是 `{"code":0,"data":{chunks, doc_aggs, total}}`。chunk 只含公开发布的 `id`、`content`、`document_id`、`dataset_id`、`similarity`。正文是合成句「合成检索片段，仍须人工核对。」空模式返回 `chunks: []` 且 `total: 0`，`code` 仍为 0。业务错误沿用官方示例 `code` 102。HTTP 错误是状态 500。`hold_responses` / `release_responses` 让 timeout 模式在记下请求后停住。

这些模式只作用于检索 POST。健康检查固定返回发布文档里的依赖项均为 `ok`。

## 入口和调用顺序

pytest 夹具 `fake_ragflow` 在 `tests/backend/conftest.py`。测试用标准库直接访问这个地址，不经过 `EvidenceCandidateService`，也不注入传输层。`retrieval.py` 没有引用本文件。

## 数据与状态

请求记录留在进程内存，关闭夹具即消失。不写 MySQL，不写数据集，不改 `kb_sync_status`。`dataset_ids` 与 `rerank_id` 只被记下，不解释成公司或重排产品。

## 关键判断与异常

未知路径返回 404。未知 mode 返回 500，避免被看成检索成功。零命中的产品语义是跳过，不是成功的空候选；本文件只返回空信封，不做这条映射。

## 真实端点

标记 `live_ragflow` 的测试会请求环境变量 `ICG_RAGFLOW_BASE_URL` 上的 `GET /api/v1/system/healthz`。`ICG_RUN_REAL_RAGFLOW_TESTS` 不是 `1` 时，该测试在调用前跳过，原因是 `real RAGFlow endpoint tests require ICG_RUN_REAL_RAGFLOW_TESTS=1`。`true` 或其他值同样跳过。CI 不设置这个变量。健康检查按发布文档不带 Authorization。真实检索要有注入的 dataset id，不在本卡。
