为什么有这个文件：说明幂等键如何查找、保存和过期。

它解决什么问题：避免两套重复请求记录各记各的，或把失败结果当成可以无限重放的成功。

# BE-M0-T03：代码解释

- 对应任务：[BE-M0-T03](../tasks/BE-M0.md#be-m0-t03)；Issue：[ISSUE-005](../../issues/ISSUE-005.md)；交付：[BE-M0-T03](../delivery/BE-M0-T03.md)
- 日期：2026-10-12。主要代码是`icg_demo/idempotency.py`，由工作流、服务承诺和旧章节提交调用。

## 改了什么以及为什么

v1写操作和旧章节提交原先各有一套重复请求记录。现在都使用`DemoState.workflow_receipts`。键是`(scope_id, user_id, idempotency_key)`。指纹是动作、请求体和`If-Match`的规范JSON摘要。

成功结束后`remember`写入回执。`DomainError`发生在事务内时，内存仓库不提交，因此失败没有回执。解析失败仍会保存失败任务并增加版本，这是原有业务行为；但`remember`会跳过`job.status == failed`，同一键可以再试。再试时必须带新的`If-Match`，因为版本已经增加，指纹也变了。

## 入口和调用顺序

1. 中间件把当前请求放进上下文，供稍后标记重放。
2. 路由用头别名`Idempotency-Key`读取标记。格式检查在业务层完成，返回428，不在框架层变成422。
3. 写入前`lookup`。过期、缺少创建时间或结果是失败的回执会被丢掉。
4. 命中且指纹相同：返回第一次的成功结果，并在请求上标记重放。响应中间件据此设置`Idempotent-Replayed: true`。第一次成功和失败都不发送这个头。
5. 命中但指纹不同：409，不调用本次写入。
6. 未命中：执行业务。成功后`remember`，然后`enforce_bounds`。

旧章节提交先核对编辑权，再查回执。正文标记仍必填。头和正文不一致时409，消息说明两者不一致。

## 数据与状态

回执保存在进程内存，不是数据库。过期时间86400秒，上限`MAX_IDEMPOTENCY_RECEIPTS = 2048`。超限时按创建时间和键排序，保留较新的记录。测试可以替换这个上限。比较时间用`DemoService`的时钟，测试可以拨快。

公司资料和服务承诺模板的`scope_id`是`library:{company_id}`。它们没有项目编号，不能假装属于某个项目。

## 关键判断与异常

同一账号在同一项目对两个章节使用同一个键，会得到409，因为scope是项目而不是章节。动作名里含章节编号，所以指纹不同。这是契约选择，交付里已写明。

客户端重试说明写在OpenAPI的`info.description`和`components.x-idempotency.retry`。服务端不自动重发。

## 验证与限制

专项测试覆盖重放头、冲突且无副作用、缺键、过短键、失败后可重试、满24小时后同一键成为新请求，以及上限为1时丢掉最旧回执。全量结果见[验证记录](../testing/2026-10-12-error-idempotency.md)。重启后的回执恢复、多进程共享和前端自动重试都还没有。
