为什么有这个文件：解释本节编写人、独立方案确认和分册操作的实际调用关系。

它解决什么问题：避免一章的准备进度拖住全部章节，或把确认人和生成依据混为一谈。

# APP-M1-T15：逐章分工与独立方案确认代码解释

日期2026-10-11，ISSUE-007；交付见 [T15](../delivery/APP-M1-T15.md)。依赖 [T14成员权限](APP-M1-T14.md) 和已有本章写作输入。

## 页面到后台

编辑台目录显示本节编写人和方案确认状态。`WritingPlanReview.tsx` 按后台权限提供全项目、本册或本人本节的操作范围：项目负责人可处理全部，分册负责人只调整本册，本节编写人只保存和确认自己的章节。

本节保存调用 `PATCH /api/v1/projects/{project_id}/chapters/{chapter_id}/plan`，保存选定事实、要点和字数目标，并进入待确认。独立确认调用同路径的 `POST /confirm`；人员调整使用独立 `PATCH /assignment`，不是借保存文字修改人员。未保存的标题、分册或人员调整会阻止确认，避免“以为确认了屏幕上新结构，后台实际仍是旧结构”。

批量大纲请求携带 `scope=all|technical|business`，只传本范围章节；后台保留其他册。检查和内部输出也带分册范围，分册负责人只能操作自己的册，项目负责人可处理两册。

### 防止旧方案覆盖新方案

`writing-input.ts` 为每一节分别记录表单读入时的依据，包括标题和人员、方案、相关事实、条款、证据及来源。`WritingPlanReview.tsx` 在保存、分工调整、确认和批量确认前比较这些依据；后台版本号更新不会自动把旧表单变成“已经核对过”的新表单。

发现变化时，当前填写内容仍留在页面，相应写入暂停。使用者打开“核对并载入最新本节方案”查看后台值后，才能替换该节表单；核对窗口打开期间后台再次变化，也拒绝使用刚才的旧核对结果。成功保存某一节只更新该节的依据，不会顺带认可其他节。章节新增、删除、移册和排序变化另有整个操作范围的核对，批量确认不能漏掉这些变化。

这解决的是多人协作中的旧表单误覆盖。后台仍以当前版本和权限作最终判断；页面保护与后台保护要同时成立。

## 确认和生成依据

`generation_context.py` 为每章保存确认人、时间和实际来源摘要。摘要相当于本章依据的指纹：包括本章条款、证据、选定事实、必备事实、要点、标题、人员和负责人资格。正文提交不会把相同方案退回；无关章节要点变化或增加只读成员不会自动撤销本章确认。

`workflow.py` 确认前检查解析是否已人工确认、本册有负责人、条款已分配到有效章节，以及事实和证据当前可用。失败回滚整次操作。技术章独立确认后可生成，商务章仍可准备；全项目 `plan_confirmed` 只是全部章节状态的汇总，不能代替本章门禁。

生成和整章建议仍共用输入组装器，保存当次来源快照。调用前及结果保存前均核对当前权限、输入和正文版本；结果先作为候选，人工核对后才能提交正式正文。

## 编辑与撤权

`EditorPage.tsx` 读取当前章节 `permissions` 和 `writing_input.is_current`，不根据公司经理标签推断权力。取得编辑权、续期、草稿保存和提交都由后台再次检查。撤权后旧编辑权失效，页面保留尚未提交的文字，关闭写入入口；同项目接手人只看到正式正文和自己的草稿。
