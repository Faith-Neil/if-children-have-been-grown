# APP-M1-T14：项目成员与分册分工代码解释

日期2026-10-11，ISSUE-007；交付见 [T14](../delivery/APP-M1-T14.md)。当前为本地演示实现，模型和数据库仍使用替身与内存。

## 改了什么

公司角色表示账号可做哪类工作，项目成员表示该账号被允许进入哪个项目；两者同时满足才有操作权。公司经理账号可以创建项目，但不会因此成为其他项目的负责人。创建者自动加入新项目负责人，并默认负责技术、商务两册，之后可按实际分工修改。

新增 `backend/bid-core/icg_demo/project_access.py` 集中核对项目负责人、分册负责人和本节编写人。`project_team.py` 在同一次保存中核对成员、负责人、参与分册和交接。参与技术册仅表示分工意向，不自动取得整册修改权。

## 入口和调用顺序

1. `App.tsx` 登录后读取项目列表，后台只返回当前账号参与的项目。
2. `workflow.py` 返回项目工作区、团队和当前账号真实权限；`domain.py` 保护原有章节、草稿、版本与下载入口。
3. `ProjectSettingsPage.tsx` 保留示例的左侧锚点和分组表单；`project-team.ts` 把成员、两册负责人、合标负责人和交接理由组装成请求。
4. `PUT /api/v1/projects/{project_id}/team` 核对当前版本和重复请求标记，然后在一次事务里保存。事务就是“全部检查通过才一起生效”，失败不会留下半份分工。
5. 成功后页面用后台返回值更新表单并刷新权限；失败或版本冲突保留填写内容。基本信息和人员分工使用各自明确的保存入口。

页面还分别保存“读入表单时的基本信息”和“读入表单时的人员分工”。`project-form.ts`、`project-team.ts` 比较这两份依据与后台当前值。项目版本号变新，只说明后台有修改，不说明使用者已经看过这些修改；因此其他人改变人员后，旧表单不能拿新版本号直接覆盖。页面先保留填写内容，要求使用者查看并明确载入最新分工，再允许保存。无关操作引起版本号变化时，不会因此丢掉表单。

## 数据与交接

`DemoState.project_teams` 保存项目成员、两册负责人、合标负责人和交接记录；章节保存 `assignee_id`。账号仍是合成演示账号，没有正式邀请、密码或公司账号管理。

调整导致失去编辑权时，涉及正在编辑或已存草稿的章节必须填写交接理由。后台解除旧编辑权，保留正式正文、版本历史和每人的私人草稿。交接记录只显示保留数量和操作信息；接手人不会获得原编写人的私人草稿。本人草稿在本人重新获得访问权限后仍可核对，删除草稿要带本人草稿序号，避免误删新版本。

“参与分册”是可选项。成员可以先加入项目，暂不选择技术册或商务册；这不会授予整册编辑权。分册负责人和本节编写人必须满足所负责册的参与范围和可写资格，不能利用留空绕过限制。

## 关键限制

- 未加入项目和跨公司均返回找不到资源，不公开项目、原件或导出内容；任务列表也按项目成员过滤。
- 项目至少保留一位有效负责人。公司编写账号不能提升为项目负责人，公司只读账号不能提升为可写项目成员。
- 两册负责人必须是参与本册的可写成员。普通成员不能修改团队，合标分工不授予检查或创建输出的权限。
- 每次保存及重复请求回放都会重新核对当前权限；模型调用返回后也再核对，撤权后不保存候选。
- 页面遇到访问权撤回时冻结操作，保留已输入文字，可明确下载到本机供本人保留；不会继续向后台提交。
