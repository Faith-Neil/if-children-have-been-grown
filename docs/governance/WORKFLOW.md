为什么有这个文件：把收到项目需求到完成交付的步骤写成共同流程。

它解决什么问题：避免需求、代码、进度和验收记录各说各话。

## 统一入口和职责

| 文档 | 职责 | 更新时机 |
|---|---|---|
| [PRD](../PRD.md) | 业务需求、范围与验收；工程协作附录 | 需求、验收或协作要求变化 |
| [ROADMAP](../ROADMAP.md) | 阶段目标、里程碑、范围和完成门禁 | 优先级、依赖、范围或发布顺序变化 |
| [ARCHITECTURE](../ARCHITECTURE.md) | 模块边界、数据流、状态、接口与实现约束 | 方案、接口、状态或模块变化 |
| [任务看板](../TASK_BOARD.md) | 每个任务的状态、依赖、Issue 和交付 | 开工、阻塞、验收、合入时 |
| [Issue 看板](../../issues/index.md) | 需求变更、版本更新、Bug 和决策的统一记录 | 收到变更、分析、验收、合入或发布时 |
| [项目进度](../PROJECT_STATUS.md) | 当前真实实现、任务计数、阻塞与下一任务 | 每个任务开工、完成或阻塞时 |
| [DOCUMENT_INDEX](../DOCUMENT_INDEX.md) | 文档路径、版本、状态、更新日期与来源 | 每次新增、修改、移动、归档文档 |

看板记录任务状态，任务卡记录可实施范围，Issue 记录变更依据，交付文档记录完成证据。阶段进度由这些事实汇总；文档存在、代码已写或 PR 已创建都不能代替任务验收。

## 1. 变更先登记 Issue

每次需求变更、版本更新和 Bug 修复必须先登记或更新 Issue，关联具体任务。项目治理、技术选型和接口冻结变化也登记 Issue。编号沿用已有序列；字段和状态见 [Issue 管理](../../issues/README.md) 与 [模板](../../issues/template.md)。

记录至少包含：原行为与期望行为、来源、类型、影响范围、验收、涉及里程碑/任务、PR、基线同步表和下一步。版本更新包括软件、文档业务基线和依赖升级；升级后的版本、迁移/兼容性、验证和回退方式必须有据可查。

纯排版或文字笔误可关联当前维护 Issue，但仍更新相应记录；不能用“小改动”绕过需求、版本或 Bug 的登记。

## 2. 以任务为单位推进

1. 从 [TASK_BOARD](../TASK_BOARD.md) 找到当前依赖已满足的任务。
2. 阅读对应任务卡，核对输入、关联 Issue、涉及文件、验收和交付路径。
3. 任务范围过大时先拆成多个可单独验证的任务。0.5～4 小时是初始粒度估算，复杂任务继续拆分，不把估算当完成承诺。
4. 开工把任务标为 `in-progress`，同步 Issue 和项目进度。阻塞时写明缺少的输入与下一步。
5. 实现后按任务验收，提交交付、代码解释和测试证据，再进入 `in-review`。
6. 验收通过且完成记录齐全后，才标 `done`；PR 合入、部署和发布另列。

状态：`planned` → `ready` → `in-progress` → `in-review` → `done`。`blocked` 必须写原因，依赖满足后回到适当状态；`cancelled` 必须链接对应 Issue 的取舍结论。没有接口、基线或其他必要输入的正式应用任务不能标 `ready`。

一个任务只有一个交付单位和一组明确验收。实现任务与文档对齐任务可以分开，但前者在关闭前仍要有本次同步检查；不能把必需记录全部推给最后一个里程碑。

## 3. 每任务的完成材料

使用 [交付模板](../templates/task-delivery.md)，保存为 `docs/delivery/<TASK_ID>.md`。每份文档必须包括：

- 任务 ID、里程碑、关联 Issue、分支/提交/PR、验收与合入状态。
- 完成内容、实际变更文件、与任务范围的偏差。
- 代码解释：入口、调用顺序、状态或数据变化、关键判断、依赖、限制；有代码修改时链接 `docs/code/<TASK_ID>.md`。无代码修改明确写“无”并解释文档改动目的。
- 验收步骤、执行结果和证据；没有执行的检查明确说明。
- 项目进度：完成的任务、当前完成数、剩余任务、阻塞和下一任务。
- PRD / ROADMAP / ARCHITECTURE / Issue / TASK_BOARD / PROJECT_STATUS / DOCUMENT_INDEX 的同步结果。

代码解释使用 [说明模板](../templates/code-explanation.md)，说明实际代码，不用计划中的模块冒充实现。解释文档与相关代码同一变更更新。

任务交付顶部保留 `task-delivery` 两列表，供检查程序验证任务 ID、代码解释、验收和项目进度都有记录；详细内容在正文展开。进度快照以当时结果为准，后续汇总以项目进度和任务看板为准，不改写历史完成事实。

## 4. 四份基线每次做同步检查

每个变更收尾都核对 PRD、ROADMAP、ARCHITECTURE 和 Issue 看板。其治理块与本流程保持同一版本、日期和 Issue；业务版本各自独立，不要求版本号相同。

| 核对对象 | 必须检查 |
|---|---|
| PRD | 范围、页面、业务规则、验收是否改变 |
| ROADMAP | 任务、优先级、依赖、里程碑出口或发布顺序是否改变 |
| ARCHITECTURE | 模块、状态、数据结构、接口、部署或技术约束是否改变 |
| Issue 看板与详情 | 当前状态、决定、影响、任务、验收证据和下一步是否一致 |

有影响则同步正文、文档版本和修订记录；无影响则在 Issue 与交付的同步表中写明理由，保留原业务正文。不能仅复制一个版本号便宣称需求、计划和架构已对齐。

TASK_BOARD、PROJECT_STATUS 和 DOCUMENT_INDEX 同步更新。使用 [变更同步记录](ISSUE-003-sync.md) 记录本轮检查；后续复制相同结构按 Issue 存放。

## 5. 文档更新管理

DOCUMENT_INDEX 每个条目使用稳定编号，记录相对路径、层级、文档/治理版本、状态、最后更新日期和关联 Issue/任务。修改条目时同步日期和版本；移动文件更新索引及引用；归档条目保留替代文件和来源。参考产品原文保持原版本，不能被治理更新覆盖。

新增维护文档、任务卡、交付、测试、代码解释和模板都登记索引。检查脚本自身、测试程序也登记，便于协作者找到验证入口。不要为一个名字建立多个不同用途的索引文件。

## 6. 验收与合入

执行：

```bash
node scripts/check-project-governance.cjs
node --test tests/governance/*.test.cjs
```

行为修改另跑实际受影响的验证。检查程序验证链接、治理块、任务完成材料和索引；需求与代码的语义一致性仍由任务验收与评审确认。

本地任务 `done`、Issue `closed` 表示已完成本地验收；交付与 Issue 分别记录 PR 是否合入、软件是否发布。未合入的修复不能写成已上线。评审发现问题时重新开启原 Issue/任务并保留原验收记录。

本轮执行样例见 [FE-M0-T02 交付](../delivery/FE-M0-T02.md)。

## 7. 工作区自动快照与人工交付

工作区使用单一Git根；历史 `ICG/` 原样保留并通过 [来源清单](../source/WORKSPACE_MATERIALS.md) 管理，两个银行合同根、凭据与运行数据由用户确认排除。GitHub协作分支用于云端版本快照；main合入、软件部署及发布独立执行。

自动同步产生WIP提交以保存进行中的文件，不标记任务done或Issue closed，也不能替代上述收尾验收。人工暂存、切换分支、Git操作未完成或双方历史分叉时暂停；由维护者按实际状态处理后恢复。同步工具、运行状态和停止方式见 [操作说明](../../tools/workspace-sync/README.md)。

持续同步在当前Windows用户会话运行；退出登录、休眠、断网期间不能实时同步，恢复会话/网络后继续。令牌用户绑定加密保存在工作区外；不得复制运行配置、令牌或日志到Git文件。
