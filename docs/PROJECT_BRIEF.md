## 项目在解决什么

目标是帮助企业把招标要求、公司资料与承诺组织成有来源、可检查的投标文档：上传招标包 → 解析并人工确认 → 响应矩阵与事实/SLA → 确认写作方案 → 章节生成/修正 → 人工编辑 → 检查/定稿 → 分册Word导出。响应矩阵是“每项要求由哪里响应、用什么证据”的对照表。

一期技术、商务两册已由用户确认；最终合标、页码、签章与平台递交由人在系统外完成。合作分支技术标草稿与此范围的具体差异继续评审；详见 [一期交付建议](decisions/phase-one-scope.md)。

## 接手后最先关注的六件事

| 优先事项 | 不解决会怎样 | 下一步产物 |
|---|---|---|
| 一期范围和生成单位 | 技术/商务/资格范围与“逐条候选/章节闭环”各做一套 | 一张试点场景、角色、输入、确认点、最终文件表 |
| 漏抽与关键引用 | 已抽出的条目都正确，也可能漏掉关键否决要求；关键附件未解析仍能确认 | 原文独立标注样本、关键条款完整性与确认门禁 |
| 事实/证据变更与检查有效性 | 正文未变，事实/SLA/附件/模板变了，旧检查可能不覆盖新导出 | 依赖指纹、检查/导出快照及失效规则 |
| 前后端共同契约 | 字段、任务状态、选区、草稿、锁、错误及重试由两边各自决定 | 首批OpenAPI、稳定ID、版本/租约/幂等/任务合同 |
| 公司隔离、敏感字段及SLA | 角色菜单不等于后台授权；手机号显示与越能力承诺口径不统一 | 字段×角色×场景权限表、SLA三列交互和服务端验收 |
| 技术/部署与试点输入 | 目录先拆成多个服务，却没有共同事实源、可恢复任务及有效资料 | 选型决策、可用默认资产、最小纵向链路与目标环境 |

审查结论是：**方向能覆盖主要编标场景，但当前方案不能直接作为已冻结开发合同，也没有证据证明真实业务可用。** 缺口分为文档冲突、待细化设计、缺真实实现，不能统称为运行中的Bug。

## 建议怎样推进

继续 [FE-M0-T03/04](tasks/FE-M0.md)：统一范围和生产契约，记录 [ISSUE-005待决门禁](../issues/ISSUE-005.md)。两家公司合成样本的“登录/公司过滤 → 章节读取 → 取得编辑权 → 草稿保存 → 新版本/操作记录 → 检查/单章Word”已由[后端demo](delivery/BE-M0-T01.md)跑通；下一步接持久数据库和生产身份，再接可恢复的解析、生成任务及完整分册输出。
